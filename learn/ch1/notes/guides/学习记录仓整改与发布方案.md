## 四、架构：运行适配层

### 4.1 原理

上游实验的配置面本来就是"环境变量三件套"（key / base_url / model，E10）。路由层的解析结果可以从**外部按上游契约填槽位**，再以正确 cwd 启动上游脚本——上游代码零改动：

```
learn/ch1/run.py --exp image-workflow --task image_workflow [-- 上游参数透传]
        │
        ├─ ① from learn.agentbook.model_router import resolve     ← 自举 sys.path 到仓库根
        ├─ ② contracts["image-workflow"].apply(cfg)               ← 按上游契约注入环境变量：
        │      KIMI_API_KEY / KIMI_BASE_URL / REWRITE_MODEL   ← 上游"改写节点"槽位
        │      DASHSCOPE_API_KEY / DASHSCOPE_BASE_URL / WANX_MODEL  ← 生图工作流槽位
        │      OPENAI_API_KEY / OPENAI_BASE_URL               ← 原生生图槽位
        │      GEMINI_API_KEY=<占位非空>                       ← 仅上游 validate() 查非空
        └─ ③ subprocess 启动上游脚本，cwd=该实验目录
               → chapter1/image-gen-workflow/main.py 原样运行；相对路径缺陷同时被 cwd 规避（E9）
```

### 4.2 构成

| 文件 | 职责 |
|---|---|
| `learn/ch1/run.py` | 统一入口：`--exp <名> --task <路由> [-- 透传]`；resolve → 注入 → spawn（cwd=实验目录）→ stdout 直通；`--evidence` 模式收集输出写 `learn/ch1/evidence/` |
| `learn/ch1/contracts.py` | **上游契约表**：每个实验的"上游槽位 ↔ 路由任务"映射，逐条注释语义与验证状态（引用 t 编号）；名字按上游原变量（如 `KIMI_*` 语义 = "上游改写节点契约槽"，实际值可为任意 OpenAI 兼容厂商——真实 provider/model 由证据 json 记录） |
| `learn/ch1/variants/web-search-agent/main_route.py` | 纯新增变体入口（原 chapter1 下新增文件，迁入容器；文件头两行自举 sys.path 到仓库根后 `from learn.agentbook.model_router import resolve`） |
| `learn/.gitignore` | 目录级忽略：`ch1/evidence/*.png` 等——**不碰上游 .gitignore** |
| `learn/agentbook/`、`learn/infra/` | 路由层与探测设施（原 agentbook/、model_tests/infra/ 整体迁入） |

### 4.3 方法论收益：两轨归因纯净

- 第一轨（作者基线）：`chapter1/**/validation/` + 锚定 runner，上游原样。
- 第二轨（路由变体）：同一份上游代码，仅配置注入不同（适配层）。
- **两轨差异 100% 归因于配置，不再混入代码改动**——变量隔离比接线版更纯粹。

### 4.4 契约核实任务（执行期完成，E10 两处待核实）

- CT-1：context 实验——枚举上游 provider registry 全部槽位（`SUPPORTED_PROVIDERS`、各 provider 的 key/base_url 变量名），确定 text_only 注入的最优槽位。
- CT-2：learning-from-experience——读上游 main.py 参数面（provider/base_url/model 如何传入 LLMAgent），确定注入方式。
- Fallback：若某实验上游确无 base_url/model 覆盖位 → 该实验**保留最小接线**作为唯一例外（在 learn/README.md 声明），或走上游 PR 路线。
